## Context

NovelGenSuite はグリーンフィールドで、アプリのソースツリーがまだ存在しない（追跡対象は docs と `.claude/` 等の設定のみ）。本変更は「LLM 同士に笑点風の大喜利をさせる TUI アプリ」の最初の runnable baseline を立ち上げる。

体験は 2 面ある: (1) エンタメ — 観戦／お題投入して楽しむ番組、(2) 研究 — どのモデル・芸風がウケるかを数値化・比較するハーネス。この二面性が設計上のほぼすべての判断を駆動する。確定済みの主要前提は proposal を参照: TypeScript + Ink、複数プロバイダ混在、Seat = Persona × Model、ブラインド審査、構造化トランスクリプト、人間は MVP ではお題側のみ。

制約: API キーは `.env` 管理でコミット禁止。プロバイダごとにレイテンシ・コスト・レート制限が異なる。シェルコマンドは `rtk` 経由。

## Goals / Non-Goals

**Goals:**
- engine を UI から完全分離し、ヘッドレス実行（研究）と Ink TUI（エンタメ）の両方で同一 engine を使える。
- 複数プロバイダを統一 IF で扱い、席ごとにモデルを差し替え可能にする。
- 自己選好バイアスを構造的に避けるブラインド審査を、研究の数値化が成立する形で実装する。
- すべての実行を再採点・リプレイ可能な構造化トランスクリプトとして残す。
- 片肺故障（一部プロバイダ不通）でも番組が止まらない堅牢性。

**Non-Goals:**
- 席をまたぐ掛け合い・前のお題の引きずり・回答者同士のいじり（将来拡張）。
- 回答席／審査席への人間参戦（将来拡張。席抽象に後追いで乗せる）。
- Web UI（engine 分離で将来容易にするが、本変更では作らない）。
- 音声/TTS、座布団アニメーション等のリッチ演出。
- 本格的な統計分析パイプライン（トランスクリプトを出すところまで。集計は後続）。

## Decisions

### D1. モノレポのパッケージ分離（engine / providers / tui）
engine（状態機械・席・台帳・ルーブリック適用）を UI とプロバイダから独立させる。`providers` は LLM アダプタ、`tui` は Ink ガワ。engine は providers の「統一 IF（インターフェース）」にのみ依存し、具体プロバイダ実装には依存しない（依存性逆転）。
- **なぜ**: ヘッドレス研究実行・将来の Web 化・LLM 抜きの engine 単体テストを同時に満たすため。
- **代替案**: 単一パッケージで層を論理分割 → 速いが境界が曖昧化しやすく、研究ハーネスとしての再利用と Web 流用が難しくなる。MVP でも分離の利得が大きいと判断。

### D2. LLM 統一アダプタに Vercel AI SDK を採用
`ai` パッケージと各プロバイダ provider（Anthropic/OpenAI/Google）で複数社を 1 つの IF から叩く。engine はモデル識別子だけを知り、ルーティングはアダプタ層が担う。
- **なぜ**: 複数プロバイダ混在が前提であり、各社 SDK 差異の吸収を自前で持つコストを避ける。TS エコシステムで実績がある。
- **代替案**: 各社 SDK を直接ラップする自前アダプタ → 完全な制御は得られるが車輪の再発明。アダプタ IF を engine 側に定義しておけば、後で実装を差し替えても engine は不変。

### D3. ブラインド審査＝匿名化 + 別系統審査モデル + 順序シャッフル
審査モデルへは回答テキストのみを匿名ラベル（回答 1..N）で、順序をシャッフルして渡す。審査モデルは回答席のどのモデルとも別系統に設定できる。裁定は「席（内部 ID）→ 座布団変動 + 理由」の構造化結果として返す。
- **なぜ**: LLM-as-judge の自己選好・位置バイアスは研究の数値を直接汚す。エンタメ用途では司会の即興裁定で良いが、研究用途と両立させるためブラインドを既定の審査経路にする。
- **代替案**: 観客 LLM 群の投票（合議）→ 分散は減るがコスト増。MVP は単一ブラインド審査、合議は将来拡張のフックだけ用意。

### D4. 生成と採点の分離（トランスクリプトが中間生成物）
番組実行は「生成フェーズ（回答収集）→ トランスクリプト → 採点フェーズ（裁定）」と捉え、採点は記録済み回答を入力に再実行できる。ライブ番組はこの 2 フェーズを連続実行しているに過ぎない。
- **なぜ**: エンタメのログがそのまま研究データセットになり、別モデル再採点・人間スコア相関・リプレイが無償で手に入る。
- **代替案**: 生成と採点を密結合 → ライブ実装は単純だが再採点ができず研究価値を失う。

### D5. 回答収集は並列、失敗は席単位のパスへデグレード
回答席への呼び出しは `Promise.allSettled` 的に並列発行。タイムアウト・エラー・レート制限・キー未設定はアダプタ層が「失敗結果」として返し、engine はその席を「パス」として記録して継続する。
- **なぜ**: レイテンシ差の吸収と片肺故障耐性。番組が 1 社の不調で止まらない。
- **代替案**: 逐次呼び出し → 実装単純だが遅く、1 席の失敗が全体を巻き込みやすい。

### D6. Seat = Persona × Model の直交バインディング
ペルソナ（芸風・口調・得意技・few-shot）とモデル（駆動 LLM）を別エンティティにし、席はその組。研究では「同一ペルソナ×複数モデル」「同一モデル×複数ペルソナ」の 2 軸実験が可能。
- **なぜ**: モデル比較とペルソナ効果を分離測定できる。エンタメでも芸風とモデルを自由に組める。
- **代替案**: ペルソナにモデルを内包 → 設定は単純だが 2 軸実験ができず研究価値が落ちる。

### D7. 終了条件・ルーブリック・ペルソナは設定で外出し
終了条件（座布団 N 枚 / M ラウンド）、審査ルーブリック（意外性・お題適合・言葉のキレ等）、初期ペルソナセットを設定/データとして持ち、コードに焼き込まない。初期ペルソナは**実名・実在回答は使わない**前提のもと、キャラ性（口調・得意技・自虐/毒/天然など）を本家笑点メンバーに寄せたオマージュとして同梱する（grill 20260609 決定）。
- **なぜ**: ユーザー変更可という要件を満たし、実験パラメータをコード変更なしに振れる。笑点という前提に手触りを寄せつつ、実名・実ネタを避けて権利面を安全に保つ。
- **代替案**: ハードコード → 速いが要件（変更可能）違反。純抽象芸風 → 安全だが番組の手触りが薄い。

### D8. MVP 既定構成と司会/山田のテンプレート整形（grill 20260609 決定）
回答席は 3 席（Claude / GPT / Gemini）、審査は回答席のいずれとも別系統の第 4 モデル。司会の進行と山田くんの座布団コールは LLM 席にせず、engine が発行する構造化イベント（お題提示・回答・裁定・台帳更新）を TUI が定型文に整形して中継表示する。
- **なぜ**: ブラインド審査の「別系統」を確実に成立させつつ笑点の複数回答者感とモデル比較を得る。語りをテンプレート化することで LLM 呼び出しを回答＋審査に限定し、コスト・レイテンシ・実装範囲を抑える。
- **代替案**: 司会も LLM 席（味は濃いがラウンド毎に追加呼び出し）→ 後続拡張として席抽象に乗せる。回答 2 席（最小）/4〜5 席（高コスト）→ 既定は 3 席に決定（キー未設定社はスキップで縮退可）。

## Risks / Trade-offs

- [審査 LLM の自己選好バイアスが残存し研究数値が偏る] → 匿名化＋別系統審査モデル＋順序シャッフルで構造的に低減。将来は審査の合議化と人間スコア相関で検証。
- [複数プロバイダのコスト/レート制限が運用を圧迫] → 並列だが席数は小さく保つ。呼び出し回数をトランスクリプトに記録しコストを可視化。キー未設定社は自動スキップ。
- [LLM の大喜利がそもそも面白くない/安全フィルタで無難になる] → ペルソナ few-shot とルーブリックで方向付け。MVP は「動いて観戦できる」ことを優先し、笑いの質は反復改善する。
- [Vercel AI SDK への依存とプロバイダ API 変更] → アダプタ IF を engine 側に固定し、実装差し替え可能に保つ（D2）。
- [グリーンフィールドゆえ baseline 構築コスト] → 最小の runnable baseline（1 お題・全 LLM・観戦のみ）を先に通し、段階的に肉付け。
- [秘匿情報の漏えい] → キーは `.env` のみ、トランスクリプト/ログに秘匿情報を含めない（spec で禁止）。

## Migration Plan

新規プロジェクトのため移行なし。ロールアウトは段階的:
1. リポジトリに TypeScript プロジェクト雛形（engine/providers/tui 分離）と最小の runnable baseline を追加。
2. 1 プロバイダ＋抽象ペルソナで観戦モードを通し、トランスクリプト出力を確認。
3. 複数プロバイダ・ブラインド審査・お題投入を追加。
4. baseline 確立後、canonical な setup / lint / test / run コマンドを `CLAUDE.md` と `AGENTS.md` に記録。

ロールバック: 新規追加のため、問題時はブランチを破棄すれば既存（docs のみ）状態へ戻る。

## Open Questions

grill-changes-before-apply（20260609）でインライン確定した既定値:

- **審査ルーブリック**: MVP は「意外性 / お題適合 / 言葉のキレ」の 3 軸・等価重みで座布団 ±1 を裁定。お題無視・不適切回答は 0 または没収（-1）。重み付けは実装後にトランスクリプトを見て調整する。
- **終了条件の既定値**: 既定は M=5 ラウンドで終了。賞品ラインは N=10 枚（笑点慣習）で、到達時はその席を勝者にする。いずれも設定で変更可（D7）。
- **タイムアウト/リトライ**: 既定タイムアウト 30 秒、MVP はリトライなし（1 回失敗＝その席をパス）。プロバイダ別の差はつけない。
- **few-shot の出典**: 実在の笑点回答を転載せず、オリジナル/合成例のみを同梱する（権利安全）。
- **お題同梱リスト**: 20 件程度の汎用お題を同梱し、センシティブ題材は避ける。自由入力と併存。
- **審査経路**: MVP はブラインド審査の単一経路のみ実装する（「ショーの即興裁定」は同じブラインド審査を演出として見せるだけで、別経路を持たない）。

ユーザー確認が必要な残課題は `openspec/grill/Grill-llm-ogiri-show-20260609.md` に記録（apply ゲートはこれらの解決後に解放）。
